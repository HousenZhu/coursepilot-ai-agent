# Demo and Interview Map

## Demonstration

1. Ask for recorded quiz results. Show the model's tool call, observed result, its
   follow-up decision, deterministic values and structured fact tuples.
2. Ask for a combined recommendation. Show progress, assessment and deadline sections
   read concurrently, followed by a prioritized action rather than a record list.
3. Ask for a three-day plan. Show model-authored day indices, service-generated calendar
   dates, evidence for each task and the verified final answer. Repeat the same
   idempotency key and demonstrate that it
   returns the same result and plan ID rather than creating another plan.
4. Ask a handbook question. Show validated paragraphs and open a source at its page.
5. Request another student's private PDF. Show both API refusal and the positive owner test.
6. Change one page in a test PDF. Reindex and inspect embedded_chunks versus reused_chunks.
7. Inject an embedding failure. Verify the old active version remains readable.
8. Cancel a model request. Inspect cancelled status and absence of a committed draft plan.
9. Show the historical dispatcher report and the ReAct candidate manifest separately;
   there is no completed 180-case ReAct report yet.

## Interview discussion

- Team LMS versus individual backend ownership; why schema ownership stays split.
- JWT identity propagation, SQL allowlists and the limits of repository-based row filtering.
- Why request policy establishes scope and write intent while the model decides which
  of four tools to call, observes results and may call another tool.
- Why snapshot sections run concurrently, while plan staging waits for completed reads.
- How one-based day indices avoid model-generated calendar dates and how the service
  validates durations, evidence and the requested horizon.
- Session-level conversation locks versus transaction-level indexing locks.
- Idempotency, atomic final writes, crash reconciliation, and why failed mutations are not replayed.
- Vector/full-text score incompatibility, RRF, exact search, and retrieval versus answer metrics.
- File changes, normalized page/chunk hashes, embedding revision keys and atomic publication.
- Why source-valid output is not automatically semantically supported.
- First validated segment latency versus provider TTFT, plus measured stage costs.
- Why visible regression data and manually reviewed final data must remain distinct.

## Evidence standards

Use only completed reports generated by the version being described. Describe manually reviewed
paragraph support separately from automatic source precision. Do not claim production-scale
load, universal prompt-injection protection, or independent held-out performance without evidence.
