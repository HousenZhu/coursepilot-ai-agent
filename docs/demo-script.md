# Demo and Interview Map

## Demonstration

1. Ask for recorded quiz results. Show deterministic values and structured fact tuples.
2. Ask for a plan. Inspect the run and demonstrate that repeating the same idempotency key
   returns the same result and plan ID rather than creating another plan.
3. Ask a handbook question. Show validated paragraphs and open a source at its page.
4. Request another student's private PDF. Show both API refusal and the positive owner test.
5. Change one page in a test PDF. Reindex and inspect embedded_chunks versus reused_chunks.
6. Inject an embedding failure. Verify the old active version remains readable.
7. Cancel a model request. Inspect cancelled status and absence of a committed draft plan.
8. Open a source snapshot, attempt journal, failure case, and the actual evaluation report.

## Interview discussion

- Team LMS versus individual backend ownership; why schema ownership stays split.
- JWT identity propagation, SQL allowlists and the limits of repository-based row filtering.
- Why one typed route and independent tools are sufficient for the supported capabilities.
- Session-level conversation locks versus transaction-level indexing locks.
- Idempotency, atomic final writes, crash reconciliation, and why failed mutations are not replayed.
- Vector/full-text score incompatibility, RRF, exact search, and retrieval versus answer metrics.
- File changes, normalized page/chunk hashes, embedding revision keys and atomic publication.
- Why source-valid output is not automatically semantically supported.
- First validated segment latency versus provider TTFT, plus measured stage costs.
- Why visible regression data and manually reviewed final data must remain distinct.

## Evidence standards

Use only completed reports generated by this implementation. Describe manually reviewed
paragraph support separately from automatic source precision. Do not claim production-scale
load, universal prompt-injection protection, or independent held-out performance without evidence.
